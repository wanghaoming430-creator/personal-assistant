# 规则适用范围与升级规范

> 本文件单点定义全局、项目类型、项目专属三种规则范围，以及一条实际问题升级为正式规则的判据。其他文件需要判断范围时引用本文件，不另造近义标准。

## 一、四种处理结论

| 范围 | 含义 | 落点 |
|---|---|---|
| 全局通用 | 不依赖某个项目的目标、平台、业务数据和特殊约束；换到其他项目仍然成立 | 系统规则、助手人格、回复规范、记忆规则、全局 R |
| 项目类型通用 | 只适用于一类具有明确共同特征的项目 | `方法库/` 的方法、SOP、共享技能候选 |
| 项目专属 | 由单个项目的目标、资料、平台、流程或用户要求决定，只在该项目生效 | 该项目 `项目记忆.md`、`项目技能/`、项目约束 |
| 待验证 | 证据不足、只出现一次、边界尚不清楚 | 保留候选，不升级为正式规则 |

**默认取最小值。** 拿不准时先放项目层；只有跨项目反复出现、并能证明共同根因和共同边界时，才考虑提级。

## 二、判据

### 1. 全局通用

同时满足：

- 换成另一个项目、另一类资料、另一个模型仍然成立；
- 不依赖某个平台的功能、某个项目的专有名词或某位外部合作方；
- 能写出明确的触发信号、必须执行、禁止执行和不适用边界；
- 有真实问题作为来源，不是为“完善系统”凭空设计。

### 2. 项目类型通用

同时满足：

- 能写清这一类项目的共同特征；
- 能写清哪些项目不属于这一类；
- 至少有两个同类项目的独立证据，或一个项目内多次独立复现；
- 不把某个项目的专有名称、平台限制、人物关系写成通用前提。

### 3. 项目专属

出现以下任一情况即归项目层：

- 规则只在该项目的目标、资料、流程或交付标准下成立；
- 规则依赖该项目独有的人物、平台、供应商、格式或时间条件；
- 规则是对该项目一次具体纠错的处理办法，换项目未必成立；
- 用户明确要求“只在这个项目这样”。

### 4. 待验证

- 只出现一次，且无法判断是否会复现；
- 根因不确定，或存在多个竞争解释；
- 有反例，但反例的边界尚未查清；
- 用户只是表达偏好，没有形成可执行要求。

待验证内容可以记录、可以提醒，但不得写成“已确认规则”。

## 三、从问题到规则的路径

```text
实际使用中出现问题
        │
        ▼
保存问题证据、所属任务/项目和用户原话
        │
        ▼
检查已有 C、R、项目记忆和项目技能
        │
        ▼
分析真正根因，不先写规则
        │
        ▼
判断适用范围（全局 / 项目类型 / 项目专属 / 待验证）
        │
        ▼
检查适用边界、反例和现有规则冲突
        │
        ▼
形成修改提案，按受保护文件审批要求确认
        │
        ▼
修改对应唯一正本，记录变更和验收
```

## 四、提级条件

项目规则升级为项目类型方法或全局规则，必须同时提供：

1. **多个独立证据**：至少两个项目或两次独立场景出现相同根因，不能是同一事件的多次转述。
2. **共同根因**：说明为什么这些现象是同一类问题，而不是措辞相似。
3. **共同边界**：写清提级后仍不适用的情形。
4. **反例检查**：至少检查一个可能被新规则误伤的场景。
5. **冲突检查**：与现有全局规则、项目规则不矛盾；矛盾时保留双方证据，形成冲突提案，不自动覆盖。
6. **用户确认**：涉及系统规则、助手人格、回复规范、记忆规则的修改，按受保护文件审批执行。

缺少任一项，保留在原层级，不升级。

## 五、降级、撤销与替代

- 发现全局规则只在某个项目成立时，降级到该项目，不直接删除历史。
- 用户明确撤销或修改规则时，以新指令为准；旧规则保留编号和历史，标记“已失效”或“已替代”，并链接新规则。
- 项目结项不自动把项目规则升级为全局规则；只把结项复盘中确有跨项目价值的部分列为候选。
- 项目归档后，其规则默认不参与其他项目运行；只有新项目明确引用时才读取。

## 六、项目成功经验的处理

项目成功经验可以作为其他项目的候选参考，但不得自动复制为其他项目的有效规则。

复制前至少核对：

- 两个项目的目标、资源、平台和约束是否可比；
- 成功是否依赖该项目独有的外部条件；
- 换项目后原步骤是否仍可执行；
- 是否存在只在原项目成立的隐含前提。

## 八、验收

- 每条新增规则都能回答“适用范围是什么、依据是什么、边界在哪”。
- 项目专属规则没有出现在全局 R 表。
- 提级提案包含多项目证据和反例检查。
- 规则冲突有记录，没有静默覆盖。
